# フォーマット選定の根拠（なぜ .usst/.usc なのか）

独自フォーマット `.usst`/`.usc` を採用した理由。

## 前提: データは2種類ある

- **ツリー**: `.usst` 1ファイル。内部ノードのみを格納する（scene-A.ply 実績で 391,823 個）。
  各ノードは中心・半径・子への参照を持つのみで、描画対象そのものではない。サイズは 15.7MB
- **スプラット本体**: `.usc` の複数ファイル。65,536 個ずつ = 2MB 固定。葉 685,284 個 +
  内部ノードの代表 391,823 個 = 計 1,077,107 個（scene-A.ply 実績）。合計 34.5MB

ツリーは「どのスプラットを描くか決める地図」であり、`.usc` は「実際に描く実体」である。

## 常駐ルール（2種類で別）

- **ツリー**: 常に全部 RAM 常駐（仕様 §7.2）。部分的に持つと「どのスプラットを描くか」を
  判断できない。サイズはシーンに比例する（内部ノード数は実測で葉数の 0.57 倍）
- **スプラット本体**: 固定サイズの GPU プールに、必要な分だけを入れ替える（仕様 §6.1）

## 独自フォーマットにした理由

1. **`.usc` は解凍もデコードも不要**。ファイルのバイト列がそのまま GPU バッファのレイアウト
   （32B の SplatRecord）であり、`FileStream.Read` → `GraphicsBuffer.SetData` を中間変換ゼロで
   行える（仕様 §3.5）。Spark の `.rad` は全プロパティが deflate 圧縮されており
   （`spark-lib/src/rad.rs` の `encode_chunk_*`）、読み込みには必ず CPU 解凍が挟まる
2. **ツリーとスプラットがファイルとして分離している**。「ツリーを見て → 必要なチャンクだけ
   読む」という順序が成立する。`.rad` はツリー情報（childCount / childStart）が圧縮チャンク内の
   プロパティとして格納されているため、ツリーを引く前にチャンクを解凍する必要がある
3. **`.rad` は入力データに応じてエンコーディングが変わる**（`resolve_center_encoding` 等で
   F16 / F16LeBytes / LnF16 を自動選択する）。Unity 側で全パターンのデコーダと、メタ情報用の
   JSON パーサが必要になる。`.usst` は固定 64B ヘッダで済む

## 補足

- `.rad` は変換ツール（build-lod-unity）の入力形式のひとつとして読める。読み込み後は `.ply` を
  入力にした場合と同じ処理を通る
- Unity ランタイムが読むのは `.usst` と `.usc` のみで、`.rad` は読めない（仕様 §1.3）
